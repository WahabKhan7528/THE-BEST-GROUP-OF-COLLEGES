============================================================
1) 60-SECOND BACKEND INTRO (MEMORIZE THIS)
============================================================

Our backend is a Node.js + Express REST API with MongoDB (Mongoose).
It is modular and layered:
- app bootstrap: server.js and app.js
- route layer: defines endpoints
- controller layer: business logic
- model layer: database schemas and relations
- middleware layer: auth, role checks, uploads, error handling
- utility/service layer: token handling, cloud uploads, ID generation

Security and reliability are handled using:
- Helmet + CORS + rate limiting + mongo sanitize
- JWT access token + refresh token rotation
- httpOnly cookies for token transport
- centralized error handler for consistent API errors

============================================================
2) HOW REQUEST FLOW WORKS (END-TO-END)
============================================================

Startup:
1. server.js loads env, connects DB, configures Cloudinary, starts app.
2. app.js mounts middleware and routes.

Request pipeline:
1. Request enters Express.
2. Security/parsing middleware runs.
3. If protected route: protect middleware verifies token.
4. authorize middleware checks user role.
5. Controller performs business logic.
6. Mongoose models read/write DB.
7. JSON response returned.
8. If error: centralized errorMiddleware formats response.

============================================================
3) WHY THIS ARCHITECTURE IS GOOD
============================================================

- Separation of concerns: each folder has one clear responsibility.
- Easy to scale: add endpoints without touching unrelated layers.
- Secure by default: auth and role checks in middleware.
- Maintainable: shared logic extracted to utils/services.
- Defensible in viva: clear layer boundaries and data relationships.

============================================================
4) AUTH MODEL (WHAT TO EXPLAIN IN VIVA)
============================================================

Token strategy:
- Access token: short-lived, used for API authorization.
- Refresh token: longer-lived, used to issue new access token.

Important design choices:
- Tokens are sent via httpOnly cookies (reduces XSS token theft risk).
- Refresh tokens are hashed in DB (RefreshToken model), not stored plain.
- Refresh endpoint rotates tokens (old refresh token gets revoked).
- Logout revokes refresh token and clears cookies.
- Change password revokes all active refresh sessions.

One-line defense answer:
"We implemented session continuity with strong revocation control, not just stateless JWT, so logout and password-change security is enforceable."

============================================================
5) ROLE-BASED ACCESS (RBAC)
============================================================

Roles in system:
- super_admin
- admin
- faculty
- student

Where enforced:
- protect middleware authenticates user.
- authorize middleware checks role before controller runs.

Why this matters:
- Prevents students from calling faculty/admin operations.
- Keeps security logic centralized instead of scattering checks in controllers.

============================================================
6) FILE UPLOAD DESIGN (CLOUD + LOCAL FALLBACK)
============================================================

Upload flow:
- uploadMiddleware validates type/size and parses multipart form data.
- controllers call cloudinary utility to store media.

Storage strategy:
- Primary: Cloudinary (production-friendly).
- Fallback: local uploads folder if cloud config unavailable.

Why this is good:
- Works in both demo/dev and production contexts.
- Upload concerns are abstracted from business logic.

============================================================
9) LIKELY EXAMINER QUESTIONS + GOOD ANSWERS
============================================================

Q1: Why not put everything in one big controller?
A: We intentionally separated layers to improve testability, readability, and long-term maintainability.

Q2: Why use refresh tokens at all?
A: Short access tokens reduce risk; refresh tokens keep UX smooth and support explicit revocation.

Q3: Why hash refresh tokens in DB?
A: If DB is leaked, raw session tokens are not exposed; hash comparison still allows verification.

Q4: Why middleware-based security?
A: It enforces consistent checks for every protected endpoint and avoids missing checks in individual handlers.

Q5: Why Mongoose models with references?
A: The domain is relational (user-campus-class-subject-result), so references enforce structure and simplify population queries.

Q6: How do you handle file storage portability?
A: Cloudinary in production; local fallback in development to avoid blocking functionality.
