THE BEST GROUP OF COLLEGES - BACKEND ARCHITECTURE DEFENSE GUIDE
Version date: 2026-04-08
Scope: server folder only (excluding third-party node_modules source)

============================================================
1) HIGH-LEVEL BACKEND ARCHITECTURE
============================================================

Backend stack:
- Runtime: Node.js (ES modules)
- Framework: Express
- Database: MongoDB with Mongoose
- Auth: JWT access + refresh token strategy with cookie-based sessions
- Storage: Cloudinary (primary) with local uploads fallback
- Security: Helmet, CORS, rate limiting, Mongo sanitize, role-based access control

Layered structure in this project:
- Entry/Application: server.js, app.js
- Routing layer: routes/*.js
- Controller layer: controllers/*.js
- Service layer: services/authService.js
- Data layer: models/*.js + database/db.js
- Middleware layer: middlewares/*.js
- Shared utility layer: utils/*.js + config/constants.js

Why this structure exists:
- Keeps responsibilities separated for maintainability and easier debugging.
- Lets each layer be defended clearly in FYP viva:
  - Routes = endpoint map
  - Controllers = business orchestration
  - Models = data contracts and constraints
  - Services/utils = reusable logic
  - Middleware = cross-cutting concerns (auth, errors, uploads)

============================================================
2) STARTUP AND REQUEST FLOW
============================================================

Startup flow:
1. server/server.js starts process.
2. Loads environment via utils/loadEnv.js import side effect.
3. connectDB() from database/db.js connects to MongoDB.
4. configureCloudinary() prepares media integration.
5. app.listen() starts HTTP server.

Express app flow (app.js):
1. Security and parsing middlewares:
   - helmet, cors, cookieParser, json/urlencoded parsers, mongoSanitize, morgan.
2. Static serving for local uploaded files under /uploads.
3. Login rate limiter on /api/v1/auth/login.
4. Route mounting:
   - /api/v1/auth
   - /api/v1/public
   - /api/v1/admin
   - /api/v1/portal
5. notFound middleware for unmatched routes.
6. Central errorHandler middleware returns consistent API error payload.

Protected request lifecycle:
1. Browser sends cookies (access token).
2. protect middleware verifies token and loads user with population.
3. authorize middleware checks allowed roles.
4. Controller executes business logic.
5. Mongoose models read/write MongoDB.
6. Response sent as structured JSON.

============================================================
3) AUTHENTICATION AND SESSION MODEL
============================================================

Access token:
- Short-lived JWT for API authorization.
- Read from HTTP-only cookie.

Refresh token:
- Longer-lived JWT for session renewal.
- Stored as hash in RefreshToken model (not plain token), enabling secure revocation.

Important security behavior:
- Login issues both tokens and sets cookies.
- Refresh endpoint rotates refresh tokens (old token revoked).
- Logout revokes refresh token and clears auth cookies.
- Change password revokes all active refresh tokens for the user.

Why this design exists:
- Better security than long-lived access token.
- Supports session invalidation (logout everywhere / credential rotation).

============================================================
4) MEDIA/FILE UPLOAD DESIGN
============================================================

Upload middleware:
- multer with memory storage, file size and MIME validation.

Upload utility behavior:
- Primary path: upload buffer to Cloudinary.
- Fallback path: if cloud config unavailable, write to local server/uploads.

Why this design exists:
- Production-friendly cloud storage plus local dev resilience.
- Keeps controllers simple by centralizing upload behavior in utility functions.

============================================================
5) DATA MODEL STRATEGY (CONCEPTUAL)
============================================================

Core academic domain chain:
- Campus -> Course -> ClassRoom -> Subject -> Assignment/Material/Announcement
- StudentEnrollment connects Student to class/course/term context.
- Submission links student work to assignment.
- Result stores evaluation output and academic performance.

Identity and access domain:
- User model contains roles and role-specific academic links.
- RefreshToken supports secure persistent session lifecycle.

Administration and CMS domain:
- NewsEvent and GalleryItem power public website dynamic content.
- Mapping models (CourseSemesterMapping, AnnualYearMapping, ClassSubject) support structured academic configuration.

7) DEFENSE-READY REQUEST SCENARIOS
============================================================

Scenario A: Login and protected request
1. POST /api/v1/auth/login -> authController validates credentials.
2. authService issues access+refresh tokens and sets HTTP-only cookies.
3. Later GET /api/v1/portal/... -> authMiddleware protect verifies access token.
4. authorize enforces role if needed.
5. Controller returns domain data.

Defense point:
- This design supports stateless access checks with controlled session continuity via refresh token storage.

Scenario B: Faculty creates assignment with attachment
1. faculty calls POST /api/v1/portal/assignments with multipart file.
2. uploadMiddleware validates file.
3. portalController orchestrates create and calls cloudinary utility.
4. Assignment model stores metadata + file reference.

Defense point:
- Upload concerns are abstracted; business controllers stay focused.

Scenario C: Student submission and grading
1. student POST /portal/submissions creates Submission linked to Assignment.
2. faculty PUT /portal/submissions/:id/grade updates marks/remarks.
3. results endpoint can reflect assessed state.

Defense point:
- Clean entity boundaries: Assignment (task), Submission (student work), Result (formal academic outcome).

============================================================
8) WHY THIS BACKEND IS DEFENSIBLE IN FYP
============================================================

Strengths:
- Clear modular architecture with separated layers.
- Strong RBAC model through middleware.
- Token rotation and revocation-aware session design.
- Rich academic schema with explicit relationship models.
- CMS + academic workflow handled in same backend with route segregation.

Trade-offs and honest limitations (good for viva transparency):
- Controller files, especially admin/portal, are large and can be further split into domain services.
- Local upload artifacts can grow and need retention policy.
- Operational scripts are in same repo tree; useful, but require process discipline.

============================================================
9) QUICK VIVA Q&A CUES
============================================================

Q: Why separate routes and controllers?
A: Routes define API contract; controllers keep business logic testable and maintainable.

Q: Why store refresh token hash in DB?
A: Prevents plaintext token persistence and enables revocation checks.

Q: Why both Cloudinary and local uploads?
A: Cloud-first for production, local fallback for dev reliability when cloud config is unavailable.

Q: Why so many mapping models?
A: Academic systems need explicit term/course/class/subject relationships to enforce consistency and reporting.

Q: What happens if token expires during active session?
A: Refresh endpoint rotates refresh token and issues new access token without forcing login.
